# 長期運用時の懸念事項

司令塔からの品質面レビュー依頼(2026-08-21)を受けて、`starrydata-mcp ingest` を長期間・日次で
動かし続けた場合の懸念を実装ベースで洗い出した記録。現時点でクラッシュや破損につながる問題は
見つかっていないが、いくつかの改善余地がある。

対象コード: `src/starrydata_mcp/infrastructure/ingestion/{pipeline,etl,downloader}.py`

---

## 1. ディスク使用量

### 1.1 結論: 累積的な肥大化はしない設計

`cache_dir`(既定 `~/.cache/starrydata-mcp/`)配下のファイルは全て**固定パス**で再利用される
(`starrydata.duckdb`, `starrydata.duckdb.tmp`, `starrydata.duckdb.tmp.wal`, `staging/`,
`state.json`, `ingest.lock`)。実行日時をファイル名に埋め込むような設計にしていないため、
「実行のたびに新しいファイルが増えていく」ことはない。失敗した実行の残骸も、次回`ingest`実行時に
ロック取得後の安全なクリーンアップ(`_cleanup_build_files`)で確実に片付く(§2.2)。

### 1.2 実際に発生しうる一時的な超過分

| 要因 | 規模 | 解消タイミング |
|---|---|---|
| ビルド中の一時ファイル(`staging/`のDL+解凍済みCSV、`.tmp`、`.tmp.wal`) | ライブDB(約190MB)に加えて一時的に**追加で最大約500〜550MB**(解凍後CSV計約334MB+構築中`.tmp`が最終約190MBまで成長、これらが同時に存在する期間がある) | 成功時は都度削除。失敗時も次回実行のロック取得直後に削除 |
| 稼働中MCPサーバーが古いDB接続を握ったままの期間 | 旧DuckDBファイル1本分(現状約190MB) | `DuckDBConnectionProvider`が次回のツール呼び出し時にmtime変化を検知して自動的に接続し直し、旧接続をclose(詳細は[TECHNICAL_OVERVIEW.md §3.3](TECHNICAL_OVERVIEW.md)参照)。**アイドル状態が続く限りは解放されない**点に注意 |
| ingestが長期間失敗し続けた場合の`staging/`等の残骸 | 上記ビルド中ピークと同程度、最大約550MB | 次に`ingest`が(手動でも)成功する/少なくとも起動するまで放置される。cronが黙って壊れていると気づかず溜まり続けるわけではないが、**気づかれないまま止まったまま**にはなりうる |

### 1.3 ゆるやかな成長要因(想定内)

Starrydata本体のデータが増え続ける限り、`starrydata.duckdb`自体のサイズは**緩やかに増加し続ける**
(現状約190MB、papers/samples/curvesの行数増加に比例)。急激な肥大化ではないが、数年単位の運用では
数百MB〜数GB規模になる可能性を見込んで空き容量を確保しておくべき。

### 1.4 未対応のギャップ

- **ディスク空き容量の事前チェックが無い**。空き容量不足のままビルド中にディスクフルへ達すると、
  DuckDBの書き込みが生のOSレベルエラーで失敗する。`run_ingest`の`except BaseException`で
  `.tmp`/`.tmp.wal`のクリーンアップ自体は走るので状態は壊れないが、ユーザーへのメッセージは
  「ディスクが足りない」ではなく生の例外になる。
- **過去スナップショットの世代管理が無い**。常に「最新1本」のみを保持する設計であり
  (ディスク使用量的には望ましい)、「昨日の版に戻したい」という要求には対応していない
  (現状スコープ外、要望が出れば別途検討)。
- **永続ログファイルは書き出していない**(標準出力/標準エラーのみ)。ログ肥大化の心配はない一方、
  過去の実行履歴を後から追う手段が`state.json`の`db_snapshot`1件しか残らない。

## 2. 公開ZIP(GitHub Releases配布CSV)のスキーマ変更への耐性

### 2.1 現状の防御レベルはフィールドによって異なる

`infrastructure/ingestion/parsing.py`のJSON系パーサ(`parse_issued_date`, `parse_authors`,
`parse_string_list`, `parse_float_list`, `parse_sample_info`, `strip_crossref_quoting`)は
**全て例外を飲み込んで安全側(空文字列/空リスト/None)にフォールバックする**設計になっており、
値の**中身の形が変わる**分には強い(例: `issued.date_parts`の要素数が変わる、`author`の
キー構成が変わる、等)。

一方で、**CSVの列自体が変わるケース**への耐性は列ごとに異なる:

| ケース | 現状の挙動 |
|---|---|
| 新しい列が追加される | 無視されるだけで問題なし(`csv.DictReader`はヘッダ名ベース) |
| 列の順序が変わる | 問題なし(ヘッダ名ベースのため) |
| **省略可能フィールド**(DOI, URL, ISSN, comments等、`row.get(...)`でアクセス)が消える/改名される | 空文字列/Noneとして扱われ、**クラッシュしない**が値が静かに空になる |
| **必須フィールド**(`SID`, `sample_id` — `row["..."]`で直接アクセス)が消える/改名される | **`KeyError`で即座にクラッシュ**する。ただし安全にクラッシュする(§2.2参照): ライブDBは無傷、`.tmp`/`.tmp.wal`は例外処理で片付く |
| `manifest.json`のトップレベルキー(`generated_at`, `db_snapshot`, `totals`, `all_data`)や `all_data[project]`配下のキー(`filename`, `rows`, `bytes`, `sha256`)が変わる | `downloader._parse_manifest()`は`.get()`を使わず直接アクセスしているため同様に**`KeyError`で即座にクラッシュ** |

### 2.2 「安全にクラッシュする」ことの意味

上記のクラッシュはいずれも `run_ingest()` の `try: ... except BaseException: cleanup(); raise`
(pipeline.py)の内側で起きるため:

- ライブの`starrydata.duckdb`は一切書き換わらない(atomic renameより前でクラッシュするため)
- `.tmp`/`.tmp.wal`/`staging/`は例外送出前にクリーンアップされる
- 次回`ingest`実行にも支障は残らない

つまり**データ破損や「動かなくなる」リスクはない**が、エラーメッセージは生のPythonトレースバック
(`KeyError: 'SID'`等)になり、ユーザー(オーナー含む)には原因(「Starrydata側がCSVスキーマを
変更した」)が直感的には伝わらない。

### 2.3 未対応のギャップ・改善案(優先度低、いますぐの対応は不要)

- 必須フィールド(`SID`, `sample_id`)へのアクセスや`manifest.json`のキー参照を、
  「スキーマが変わった可能性がある」ことを名指しする独自例外(例: `UpstreamSchemaChangedError`)
  でラップし、`cli.py`側で分かりやすいメッセージに変換する余地がある。
- 省略可能フィールドの**静かな空文字列化**を検知する仕組みが無い。例えば「`author`列が
  全レコードで空配列になった」ような回帰は、ETLは正常終了してしまうため気づきにくい。
  `manifest.json`の`totals`と実際にロードした行数の突合(既に`build_database`は行っている
  訳ではないので要検討)や、主要フィールドの非空率を`get_dataset_info`的な健全性チェックとして
  出すといった案が考えられるが、現状は未実装。
- テストのfixture CSV(`tests/fixtures/raw/*.csv`)は調査時点のスキーマを固定的に模したもので、
  上流の実スキーマが変わってもテストは追従して検知できない。定期的に本物のGitHub Releases
  データに対して`ingest`を実際に走らせるカナリア的なジョブ(CI等)があれば早期検知できるが、
  現状は無い(本タスクの対応範囲外として記録のみ)。

## 3. まとめ

| 項目 | 評価 |
|---|---|
| 累積的なディスク肥大化 | **無し**(固定パス設計・確実なクリーンアップにより長期運用でも増え続けない) |
| データセット自体の緩やかな成長 | 想定内(Starrydataの成長に比例、急激ではない) |
| 一時的なディスク超過(ビルド中) | 最大約550MB、想定の範囲内だが空き容量の余裕は見ておくべき |
| ディスクフル時の挙動 | 状態は壊れないが、エラーメッセージが不親切(生のOSエラー) |
| 必須フィールドの上流スキーマ変更 | 安全にクラッシュする(データ破損なし)が、エラーメッセージが不親切 |
| 省略可能フィールドの上流スキーマ変更 | クラッシュせず静かに空値化する(検知の仕組みは無い) |
| テストによる上流スキーマ変更の検知 | 無し(fixtureは調査時点のスナップショット固定) |

いずれも「今すぐ直すべき不具合」ではなく、公開判断(Issue #15)後の運用フェーズで実際に
問題が顕在化した場合に着手すべき改善候補として記録する。
